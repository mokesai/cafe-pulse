# Cafe-web → Cafe-pulse migration map

Hand-authored mapping document for MOK-86. Based on the auto-generated schema diff at [`scripts/migrate-from-cafeweb/state/schema-diff-summary.md`](../scripts/migrate-from-cafeweb/state/schema-diff-summary.md) (regenerated by running `00-schema-inventory.ts`).

**Scope**: migrate the JMC Pastry & Coffee tenant from `cafe-web-app-prod` (ref `etihvnzzmtxsnbifftfh`) into the multi-tenant `cafe-pulse-dev` (ref `ettmabcwfhidcpapphgm`), then replicate to `cafe-pulse-prod` (ref `tjxarjzohmwqiqdruczv`).

**JMC tenant on cafe-pulse-dev**: slug `jmcpastry`, id `e29403c1-0ec9-4e28-a72a-579524dee31b` (bootstrapped in Phase 1, MOK-87). Downstream scripts read this from `scripts/migrate-from-cafeweb/state/tenant-config.json`.

**Totals**: source = 49 base tables + 2 views, 16,316 rows. Target = 61 base tables + 2 views. Delta: 12 new tables on target, 0 tables dropped.

**The one transform that dominates the migration**: almost every table gains a `tenant_id` column on the target. Every insert needs `tenant_id = <JMC tenant UUID>`.

## Key structural findings

1. **Menu ≡ `cogs_products` + `cogs_sellables`.** The old app expresses the menu through the COGS lens:
   - `cogs_products` (212 rows): the Square catalog item (e.g. "Latte") — has `square_item_id`.
   - `cogs_sellables` (391 rows): each purchasable variation (e.g. "Latte / Large") — has `square_variation_id` and a `product_id` FK to cogs_products.
   - There is **no `menu_items` / `menu_categories` table** in either schema. My original plan's "catalog" phase actually means migrating these two cogs_* tables.

2. **Order history ≡ `sales_transactions` + `sales_transaction_items`.** The `orders` and `order_items` tables are **empty in source** (0 rows) — the old app captured order history exclusively through Square sync into the sales_transactions table.
   - `sales_transactions` (4,930 rows): one row per customer order (square_order_id, tender_total_money, customer_name, ordered_at, raw_payload).
   - `sales_transaction_items` (7,308 rows): line items per order, tied to inventory items for COGS impact.
   - **Implication**: Phase 2.6 migrates `sales_transactions` + `sales_transaction_items`, not `orders`/`order_items`. Those stay empty on the target tenant (new orders will start populating once Square is re-authorized post-cutover).

3. **Invoices gain 11 new columns in target** — all for the Agentic AI pipeline (`pipeline_stage`, `pipeline_error`, `pipeline_started_at`, `pipeline_completed_at`, `vision_confidence`, `total_fees`, `supplier_fees`, `fee_source`, `fee_cogs_distributed`, `open_exception_count`, plus `vision_item_confidence` on invoice_items). Historical invoices: set pipeline columns to NULL, status to `confirmed`, pipeline_stage to `completed`.

4. **COGS tables that are empty in source but exist in target** (cogs_periods, cogs_reports, cogs_product_recipes, cogs_sellable_aliases, etc.) are not migrated — the new COGS pipeline will populate them fresh once live.

5. **Profiles schema is identical** (same 7 columns). Simplest migration: straight copy with `tenant_id` added and `user_id` set to NULL per the agreed auth strategy.

### Data tables — migrated

#### `profiles` — 3 rows

- **Target**: `profiles`. **Schema note**: profiles has **no** `tenant_id` — profiles are global to the platform, not per-tenant. Customer-to-tenant relationship is implicit via `sales_transactions`.
- **FK constraint**: `profiles.id` → `auth.users(id)`. Cannot insert a profile without a matching auth user.
- **Columns**: id, email, full_name, phone, created_at, updated_at, role. Identical in both schemas.
- **Existing trigger**: `on_auth_user_created` (from `20250101000000_initial_schema.sql`) auto-creates a profile when a new `auth.users` row is inserted. No first-signup-join trigger needed — the auto-create handles it.
- **Migration behaviour** (implemented in `02-profiles.ts`):
  - For each source profile, look up target auth user by email.
  - If target auth user exists: sync `full_name` / `phone` from source to target (only when target field is null — never overwrite richer target data).
  - If no target auth user: **skip**. Customer will self-register post-cutover, trigger auto-creates their profile, historical orders remain identifiable via `sales_transactions.customer_name`.
- **Result on cafe-pulse-dev**: jerry.mccommas@gmail.com synced (full_name + phone set). The other 2 source profiles skipped (no auth users on target).
- **Linkage to historical orders**: `sales_transactions` does not FK to profiles — it stores `customer_name` as plain text. Historical orders keep their identity regardless of whether the customer ever re-registers.

#### `suppliers` — 13 rows

- **Target**: `suppliers` + `tenant_id`. Otherwise a clean column map.
- **Notes**: Source UUIDs can be preserved (new tenant_id alone guarantees uniqueness).

#### `inventory_locations` — 5 rows

- **Target**: `inventory_locations` + `tenant_id`.
- **Notes**: Confirm target doesn't auto-seed default locations. If yes, update rather than insert.

#### `inventory_unit_types` — 8 rows

- **Target**: `inventory_unit_types` + `tenant_id`.
- **Decision pending**: verify whether target seeds a global set via migration. If so, **SKIP** this migration — source's 8 rows are probably a subset of target defaults. If not seeded, migrate as-is.

#### `inventory_items` — 292 rows

#### `inventory_item_cost_history` — 195 rows

#### `invoices` — 96 rows

- **Target**: `invoices` + `tenant_id` + new pipeline columns.
- **Transforms for historical invoices**:
  - `status` → `'confirmed'`
  - `pipeline_stage` → `'completed'`
  - `pipeline_started_at` → copy from source `processed_at` if present, else `created_at`
  - `pipeline_completed_at` → copy from source `confirmed_at` if present, else `processed_at`, else `created_at`

  - `vision_confidence` → copy from source `parsing_confidence` (semantically close)
  - `total_fees`, `supplier_fees`, `fee_source`, `fee_cogs_distributed` → NULL / defaults

- **Watch-out**: inserts must **not** trigger the invoice-pipeline webhook. The webhook filters on `status='uploaded'`, so inserting with `status='confirmed'` naturally bypasses it.
